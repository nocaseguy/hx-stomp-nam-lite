# HX Stomp firmware notes

A working document for anyone (human or agent) continuing the custom-firmware work. It records what has been learned about the HX Stomp 3.80.0 firmware, the tools used to learn it, and what is still open. **Add to it as you learn things**; see [How to contribute](#how-to-contribute).

Every claim carries a status:

- **[verified on unit]**: seen working on a real HX Stomp.
- **[verified offline]**: checked in the simulator, by disassembly, or by a checksum, not on a unit.
- **[hypothesis]**: reasoned, not yet checked. Treat with suspicion.

No Line 6 code or data is in this repository. Addresses below are facts about the stock 3.80.0 file you supply yourself (`HX_Stomp_v3.80.0_0x103966115.hxf`, MD5 `a2cd8f4ae56f49415380270ebc484bf1`, gitignored). Every patch asserts the stock bytes it replaces before writing.

## Goal and working method

Goal: a completely custom firmware for the HX Stomp, built in small steps, each verifiable on the real unit.

- The repo is a **binary patcher**: `build.py` reads the user's stock `.hxf` and writes `build/HX_Stomp_v3.80.0_CustomOS.hxf`.
- Test on the unit by running the image from RAM (nothing is written to the Stomp; power-cycle restores the installed firmware). See [RAM_RUN.md](RAM_RUN.md).
- **A RAM run keeps the application's eMMC writes in SDRAM** (`hxf_ram.py run` prints `writes: ram`, the default): Global Settings, presets and IRs changed during the run are gone at power-off, so a value set in a RAM run never reaches the next boot. To test anything that must survive a power-cycle (a setting's persistence), run with `hxf_ram.py run <build> --stock <stock .hxf> --writes pass`: writes outside the firmware overlay then go to the real eMMC (they change the unit's real settings), while the firmware itself still runs from RAM. `hxboot` has no flag for it; run its steps by hand with `--writes pass` on the last one.
- **Always build to `build/HX_Stomp_v3.80.0_CustomOS.hxf`.** Earlier "freezes" were the user running a stale, differently named file. Tell the user the MD5 of what you built.
- The user hates repeated manual readings ("I cannot be providing reading after reading after reading"). Prefer making unknowns **runtime parameters** (Global Settings knobs) so one image can test several hypotheses.
- Do not install anything on the user's machine. Do not commit or push unless told. Do not add attribution lines to commits.

## Container formats

- `.hxf` wraps an **L6IA archive** of 15 entries (`tools/l6ia.py`, `tools/hxf.py`). `tools/l6ia_verify.py` checks every checksum; a build must print `ALL OK`.
- **Entry 0**: the Cortex-M4 application (LPC4350). Segment 6 is code at `0x28d8fa80` in SDRAM and is writable at runtime. Patches append "caves" to segment 6 and reach them with `b.w` hooks or `ldr.w pc,[pc,#0]` tail-jumps. The file stores words halfword-swapped; `patch_amp.get_entry_swapped` and `_e0_vaddr_to_foff` handle that.
- **Entry 2**: the SHARC (ADSP-2156x) DSP boot stream, LDR blocks. Tag 5 = 48-bit instructions, tag 4 = 32-bit data.
- **Entry 3**: the model table (29 models; metadata such as `gainReductionMeterCount`).
- **Entry 4**: DSP graph blobs. Blob 0 is the composite library (each effect is a composite of primitives). The graph surgery format is only partly understood.
- Internal CRCs must be fixed after editing Entry 0 (`l6ia.fix_internal_crcs`).

## The M4 (CPU) side

- Thumb-2 disassembly: Apple `llvm-objdump` (`llvm-objdump -d --triple=thumbv7em`) works. A disassembly of segment 6 is the main map; rebuild it with `tools/l6ia.py`/`patch_amp.py` helpers to extract Entry 0, then disassemble.
- **Assembling M4 code: Apple `clang -target thumbv7em-none-eabi` works** as a Thumb-2/VFP assembler. `tools/m4asm.py file.s` prints the `.text` hex. Use `mul`, not `muls`, in the clang syntax where it complains.
- The firmware uses the hardware FPU elsewhere, but new M4 hooks avoid VFP because the FPU context of the thread they run in is unknown.
- Thumb function pointers are called with the address OR 1.

### Settings (Global Settings) [verified on unit]

- Global Settings has 6 stock sections; `tools/patch_menu.py` adds a 7th, **"CustomOS"**. Entries are identified by a setting ID and carry a label (`b'Section\nName'`), a limits object, and a value-string table.
- Shipped: **Tuner Activation** (Hold/Press, ID 29) and **Lock Tuner Settings** (Off/On, ID 104). `HX_DSP_METER` builds add **DSP Disp** (Used/All, Free, Used%; ID 101, which the old `dsp-meter` test images had on 102) on a page of its own.
- **Value strings show 8 characters, on one line** [verified on unit]: longer ones are cut off, and unlike the labels a `\n` does not start a second line.
- `GET_VALUE` at `0x28e1f844` (call as `0x28e1f845`): `(id, out)`, result at `[out+4]`; the buffer must be at least 8 bytes.
- Limits code for an int 0..3: `0x28e1ed1c`.
- `HX_PROBE` reuses IDs 29 and 104 for its knobs and so disables the tuner features. `HX_GR` has no Global Settings: the meter is set by the compressor block's GR knobs. (Earlier GR images used IDs 102, 128 and 126 on a second CustomOS page; the settings reader `0x28e1f844` keeps IDs up to `0x95` in one store, and those three have empty labels, the stock 0..1 limits entry, and no stock reader.)
- **Pages** [verified offline]: the generic category case reads slot `table[page * 3 + slot]` (halfword IDs, `0x17e` = empty), and the per-category array at `0x28e3b588` holds page counts (stock 3, 4, 2, 1, 4, 1); CustomOS's entry is the number of its pages.
- **Features** (`tools/features/`, one module each, see its `__init__.py`): a feature declares its `SETTINGS`, its `FLAG` and its hooks (`apply`); `patch_menu.py` gives each enabled feature its own CustomOS pages, writes the labels, limits (0..1: the stock enum entry; anything else: a snippet in the tail of the ID's long label slot, so labels stay short) and value text, and assembles its M4 `.s` at build time (`Patch.module`) with a generated `customos.inc` (`SETTING_<FEATURE>_<KEY>`, `_MAX`, `_DEFAULT`, and `CUSTOMOS_SETTING_GET`, which clamps a stored value to the setting's range). Every write goes through `Patch.put`, which fails on overlap; a place several features hook (the Home paint, the DSP stream callback, a function's start) is shared with `chain_ptr`, `chain_bl` or `chain_entry`, one stub calling every feature's handlers around the stock function.
- **Beyond Entry 0 and on/off flags.** A hook no stub can share (a function with stack arguments, or a handler that rewrites them, such as the 9-argument text renderer at `0x28db7aa4`) is taken whole with `Patch.own_entry`: a plain `b.w` to the handler, the stock prologue moved to the cave as `hook.stock`, and a build failure if a second feature owns, chains or writes over it. `p.entry(n)` gives Entries 7 and 8 (the image store, read with `tools/image_store.py`) with the same overlap check; Entry 8 grows by `add_item`, which appends the items and a copy of the item table and repoints header words 2, 3 and 5, so no stock byte moves and readers must follow word 3. `p.add_glyph` fills an empty font slot that way. A feature's `FLAG` may be a tuple, and `INPUTS` (`features.Input`: text, a choice, a path, a `key=value` mapping) give it values from the environment, read with `p.input`.
- **IDs** (`tools/setting_ids.py`): one line per ID, with its owner and the settings it held in earlier builds (a unit keeps values by ID). Of the main store's empty-label IDs, only 102, 104, 126 and 128 have the stock 0..1 limits entry; `python3 tools/setting_ids.py free <stock .hxf>` lists the empty-label IDs not yet in the file, with the stock reads and writes found for each. **[verified on unit]** 63, 74, 78, 101, 120 and 132 have no stock read or write and hold their stock limits value (100, 1, 0, 0, 1, 0), so they are spare; 105..116 hold their stock default too (see below). **Persistence [verified on unit]**: in a `--writes pass` run, ID 74 set to 5 (an engine setting with its own limits) and the stock MIDI Thru set to On both survived a power-cycle and a boot of the stock firmware; ID 63 read 100 (its stock value) at the start of that run, so an earlier 3 set on it was lost; it may have been set only in a plain RAM run (`writes: ram`), and was not retested.
- **Limits types** [verified offline]: the `movs r3,#type` of an ID's limits code: 1 a bool (XLR Outputs, Thru MIDI, ...), 2 an int (most), 3 a float (BPM, Preset BPM, the Variax knobs, Wireless Gain). Type 3 at `0x28e1ecbc` (IDs 105..116) loads default `0x3f800000` (1.0f) and min 0, so their stored 1.0f reads as a large int; that is why a probe showed them outside 0..254.
- **IDs 105..116** [verified offline]: no stock `GET_VALUE` or setter call names them, directly or through a register. The only code that does is the bulk loop at `0x28de9e5c` (called from the Global Settings menu code at `0x28dcf314` and from `0x28e206b2`, `0x28e207cc`), which reads each ID 1..136 and writes it back through the setter `0x28e1f8f4` (how = 8), skipping 32, 34, 33..56 (the Variax block) and 105..116 (`sub r3,r4,#0x69; cmp r3,#0xb`). **[hypothesis]** they are Variax per-string values (6 Global + 6 Preset, floats defaulting to 1.0), dead on the HX Stomp, which has no VDI port. **[verified on unit]** given int limits (0..4, the engine's snippet), ID 105 shows its default and does not change when its knob turns, so 105..116 are float slots, not spare int IDs.
- **Global EQ** [verified offline]: IDs 190..200 (Low Cut 199, the Low, Mid and High bands 190..198, High Cut 200), from its own page table at `0x28001ec4` (halfword IDs, three to a page, `0x17e` empty) read by the Global EQ view at `0x28d99d48`/`0x28d99e18` as `GET_VALUE(table[page * 3 + slot])`. Views with their own page tables reach settings through a register, which `setting_ids.py free` does not trace.

### Home screen and widgets [verified on unit]

- The Home view is a static object at `0x2812a05c` (returned by `0x28d960f4`).
- The divider is four 80 px segment widgets at `0x2812a594 + 0x1c*k` (k = 0..3). Layout function `0x28dc87cc` resets them to the stock look on mode change.
- Stock: the selected segment is white and 2 px, the others grey `0x666666` (a literal at `0x28dc8b58`) and 1 px. `tools/patch_divider.py` makes the whole divider 2 px green by patching three sites (`0x28dc8808`, `0x28dc8b22`, `0x28dc8b58`). Verified on the unit.
- Widget setters (PLT stubs, Thumb): `setColor 0x28e24b98` (r0 = widget, r1 = `0xRRGGBB`, black = 0); `setSize 0x28e24b28` (r0 = widget, r1 = w, r2 = h). Both take a mutex and invalidate, so they are not free to call at high rate; cache and call only on change.
- From the ROM bodies (segment 1) [verified offline]: a widget is `[0]` colour, `[4]` position, `[0xc]` size, `[0x15]` visible, `[0x18]` canvas. `setColor`/`setSize` store the value and only mark the canvas dirty (`[canvas+0x24] = 1`); `0x28e24b00` is `setVisible(w, v)`. Nothing repaints until **`0x28db8508(full, partial)`** (96 callers; the layout ends with `(0, 1)`), which sets dirty flags `0x281f3728`/`0x281f371c` under mutex `0x281f3720` and signals `0x281f3714`, waking the UI thread.
- The ROM mutex (`0x10000500`) fails instead of blocking when `CONTROL` is 0 (interrupt or pre-RTOS), so the setters and the redraw request degrade rather than hang in such contexts.
- **Creating widgets [verified offline]**: the Home constructor `0x28dc91d0(home)` (called at boot by `bl` at `0x28d96c44`) builds each divider segment as: `0x28e24988(widget, node)` (init: zero both, visible = 1, `[widget+0x18] = node`; a node is 0x28 bytes of plain memory, the stock ones at `home+0x9e0+0x28*k`), `0x28e24a18(widget, 6)` (layer), `setColor`, `setSize`, `0x28e24af0(widget, x, y)` (setPos; x from a table at `0x28e3ab84` = 0, 80, 160, 240; y = 0x77), `setVisible(widget, 1)`. No global list: a widget appears only if a paint function handles it, in two passes [verified offline]: **erase** `0x28e24b40(fb, fb, widget)` (ROM `0x100019b4`: if the node is dirty, fill the node's damage rectangle, the union of the old and new rectangles, with black, then update the node's geometry) and **draw** `0x28e24b58(fb, fb, widget)` (ROM `0x100019f0`: if dirty and visible, fill the widget's rectangle in `[widget+0]`, then mark it clean). The stock paint erases every widget before it draws any. The node's damage rectangle (`0x10003284`) [verified offline] is the union of the old and new rectangles only when the old one has a non-zero size; an old rectangle of zero width or height is dropped, so a zero-sized widget that moves damages only its new place.
- **Painting**: the UI loop (`0x28db7fxx..0x28db80e6`) paints the topmost active view of each of two view lists into one of three framebuffers (`0x25800` bytes each, 320x240 RGB565) in turn, then shows it. Paint return values are ignored. `0x100017e8(fb, x, y, w, h, colour, mode)` is the rectangle fill (colour `0xRRGGBB`, converted to RGB565).
- **Home paint**: `0x28dc8d38(ctx, home)`, registered at boot by `0x28db86bc(paint, 0x28dc9129, home)` from a literal at `0x28d96e28`. It takes the widget lock (`0x28e24970`) first and tail-calls the unlock (`0x28e24ae8`). The layout's divider segment width is the `movs r3,#0x50` at `0x28dc87fc`.
- **Framebuffer and fill** [verified offline]: the framebuffers are at `0x28d1ce98 + 0x25800 * k` (k = 0..2), column-major: pixel (x, y) is the halfword at `fb + 2 * (240 * x + y)`, which is why widget y counts up from the bottom. After each paint, a GPDMA list (`0x281f1f6c + 0x320 * k`, set up at `0x28db8336`) copies the painted buffer into the next, so pixels written straight into the framebuffer persist like widget pixels. The fill `0x100017e8(fb, x, y, w, h, colour, anchor)` places the rectangle by an anchor 0..8: column `anchor % 3` puts x at the left edge, the centre or the right edge, row `anchor / 3` puts y at the bottom edge, the centre or the top edge (so 4 = centred, 6 = rows `[y - h, y)`). It clips to 320x240.
- **Widget types** [verified offline] (`init` stub, then the size): rectangle (`0x28e24988`, 0x1c bytes); image (`0x28e24ab0`, 0x24 bytes: `[0]` image ID, `[0xc]`/`[0x10]` x, y, `[0x14]`/`[0x18]` w, h (from the image), `[0x1c]` anchor, `[0x1d]` visible, `[0x20]` node; setPos `0x28e24c68`, anchor `0x28e24aa8`, setImage `0x28e24c18`, setVisible `0x28e24a98`; erase `0x28e24b68`, draw `0x28e24a00`); text label (`0x28e249d0`, 0x30 bytes; erase `0x28e24c90`, draw `0x28e24c30`). Every type redraws only when its node's byte `[node+0x24]` is 1. The Home view's footswitch "labels" at `home+0x2b0..0x4a8` are image widgets; its 0x30-byte widgets at `home+0x64..` are the text.
- **Two view lists** [verified offline]: `0x28db86bc(paint, handler, view)` appends a view to list A (head `0x281f35b8`), `0x28db8594(...)` to list B (head `0x281f3d2c`). Each loop (`0x28db802a..0x28db80c0`) paints the last active view of A, then of B, into the same buffer. On the main screen, A's is the Home view (bottom half) and B's the **top view** `0x2812aae0` (constructor `0x28dca5e8`, paint `0x28dca358`, registered from the literal at `0x28d96d90`): preset number (y 0xed), preset name (y 0xc5) and the signal-flow row.
- **Block slots** [verified offline]: the top view's eight block slots are image widgets at `view+0x634+0x24*k`, centre-anchored (4) at x = 90 + 20k, y = 0x93, or 0x85 when the model says the slot is on the second path (`0x28dd2a74`, model `0x2812c590` from `0x28d960ac`). An empty slot is hidden; the image comes from the block's category and on/off state (table `0x28e3abdc`, set at `0x28dc992c..`). The paint updates the slots only while `view[9]` is 0.
- **Edit view** [verified offline]: `0x28128270` (list A, constructor `0x28dc1454`, generic paint: the bottom half's parameters) and `0x281282f8` = `0x28128270 + 0x88` (list B, constructor `0x28dc2b48`, paint `0x28dc27f8`, registered from the literal at `0x28d96da0`; getter `0x28d960bc`) are the Edit view. The top half's eight block slots are image widgets at `0x281282f8+0x4a4+0x24*k`, centre-anchored at x = 41 + 34k, y = 0xb5 (0x95 on the second path; layout `0x28dc1634`), hidden when empty, images from table `0x28e3a8c0` (set at `0x28dc1a86..`). Its paint draws them whatever the mode.
- **Edit view** [verified offline]: the top strip has the block title at the left (labels `+0x5c` at x 7 and `+0x8c` at x 0x45, top edge y 0xea) and a 6x9 marker (`+0x704`, image 0x43) placed 6 px after the title (`0x28dc2026`); the top right corner is free unless the title is very long.
- **Image index** [verified offline]: Entry 7 (magic `5b21255e`, big-endian words) is the image index the firmware reads at `0x28db76b4`: header `[4]` 0x241 records of 0x30 bytes at `[5]` 0x3b10; record `[5]` height, `[6]` width (the widget's `[0x18]`/`[0x14]`), `[7]` 16 bpp, `[8]` RGB565 masks. Entry 8 (magic `2a5f3b5e`, 0x3bf records of 0x18 bytes) is probably the pixel store. Edit-view block pictures (table `0x28e3a8c0`): entries 0, 1, 4, 5 are 24x24 (off, on, selected off/on), entries 2, 3 28x40, used for the selected slot while `0x28128270[0x5c]` is 1 or 2 (`0x28d9611c`): move mode, the block lifted to the top of a taller picture. Category 19 is 18x18.
- **[hypothesis]** Calling these from the DSP-link thread during boot, before the Home view exists, is a candidate cause of a freeze after the loading bar. See [Open problem](#open-problem-the-gain-reduction-meter).

### Boot splash [verified offline]

The boot picture is drawn twice, by two programs, from two copies of the same pixels.

- **Image store**: Entry 7 is the index, Entry 8 the pixels; neither has an internal checksum. Entry 7: header `{0x5b21255e, 1, size, 0x24, n = 577, 0x3b10, 577, 0xa740, ...}`, then n name records `{off, len}` at `0x24`, then n 48-byte records at `0x3b10`: word 2 = Entry 8 index, 5 = height, 6 = width, 7 = 16 bpp, 8 = `0xf807e01f` (RGB565). Entry 8: header `{0x2a5f3b5e, 1, 959, 0x18, data_off, size}`, then `{len, off}` per item (577 images, then fonts). Pixels are raw little-endian 16-bit with **blue in the top 5 bits and red in the bottom 5** [verified on unit, and offline: stock `Play_Red`/`Icon_SwitchRed` are `0x001f`, `Play_Yellow` `0x07ff`, `Play_Blue` has its large field on top; the rect fill `0x100017e8` and the glyph tint pack `0xRRGGBB` the same way], column-major from the bottom: pixel (x, y from top) is halfword `x * H + (H - 1 - y)` (a byte-exact re-encode of the splash checks this).
- **Stage 1, bootloader** (Entry 1, SPIFI XIP at `0x14000000`): a full 320x240 copy at `0x140068bc` (file offset `0x68bc`, `0x25800` bytes), the splash with 59 black rows below. `0x14002104..0x14002114`: `memcpy(0x29f00ca8, 0x140068bc, 0x4b000)` into its framebuffer, then shows it. Shown from power-on until the app takes over. No checksum beyond the L6IA ones (the vector table does not sum to 0).
- **Stage 2, app** (Entry 0): view constructor `0x28d92708`, paint `0x28d92950`, registered by the app's init at `0x28d92cfc`. It looks up images by name (`0x28db7718(name, &index)`): `HXStomp_Splash` (Entry 7 record 527 = Entry 8 item 527, 320x181 at `0x3e0fdc`) at (160, 240), top-aligned, falling back to `Logo_HXStomp` at (160, 90); `Icon_Firmware` with the text `   Firmware  ` `3.80.0` (`0xb1b1b1`) at y = 53. The loading bar is two rects at y = 121: a 320x1 track `0x660000` and a 2 px `0xff0000` bar whose width the paint sets from a float progress (clamped to 320).
- `Screen_Boot` (record 29, 320x240, the plain black LINE 6 / HX STOMP screen) has no name reference in Entry 0 or Entry 1. **[hypothesis]** unused.
- The P36Updater trailer contains a SPIFI driver (`Common SPIFI Command Set`), so the updater can write Entry 1. Entry 1's sub-header word +4 is `0x02990963` where every other entry has `0x03800000`. **[hypothesis]** a bootloader version that decides whether the updater rewrites SPIFI at all.
- Replacing Stage 2 is an in-place, same-size write of Entry 8 item 527 (115,840 bytes), and a RAM run serves it through the overlay. Replacing Stage 1 means reflashing the bootloader: a RAM run starts the app directly and cannot show it, and a broken bootloader may also lose the DFU path, which the bootloader itself starts.
- **Splash test card** image (`build.py --splash`, MD5 `3a70f780935dbfe32ccda0eac24cd41e`): a test card with corner squares, colour bars and "CUSTOM OS" text in place of `HXStomp_Splash`. Result **[verified on unit]** (RAM run): orientation and the column-major layout are right; red and blue were swapped (the card was packed red-on-top), which went unnoticed. `pixel()`/`pixel_rgb()` now pack blue on top; `splash_topo.py`'s palette phases were swapped so its picture packs to the same bytes as the image that ran.
- **Text**: the boot view copies `   Firmware  ` (`0x28e24d14`, literal `0x28d92930`) into a 48-byte buffer at `0x2811ee38` (`0x28daad94` = strcpy), appends `3.80.0` (`0x28e24d24`, literal `0x28d92938`; `0x28daade8` = strcat), and centres the result with `Icon_Firmware` at y = 29. Each string has that one reference; the two are adjacent, 24 bytes in all. The splash feature (`HX_SPLASH_TEXT`) writes up to 23 characters there and points the appended literal at the text's NUL.
- **Full screen**: the boot view's image name (`0x28e24cf4`, 16 bytes, one reference) becomes `Screen_Boot`, and a 320x240 PNG goes into that image (Entry 8 item 29). Full-screen card image (MD5 `8d7a254bfc03232cd18fb308fe6e224e`, **not yet tested on the unit**); full-screen card + text `CustomOS 3.80.0` (MD5 `e3bf46ab7f38351806a2e0b5eee76457`, **verified on unit**: full screen, text over the picture; each glyph of the text is drawn on its own black box).
- **Glyph backgrounds** [verified offline]: a text widget (`[0]` text, `[4]` max length, `[8]`/`[0xc]` position, `[0x18]` font, `[0x1c]` colour, `[0x20]` anchor, `[0x2a]` visible, `[0x2c]` node) is drawn by `0x1000206c`, which calls the app's renderer `0x28db7aa4(fb, text, len, x, y, font, colour, anchor, mode)` with mode 0 (its only caller is the veneer `0x10003530`). Per glyph, mode 0 calls `0x100014cc`, which reads the glyph's columns straight into the framebuffer, black included, then ANDs them with the colour: a black box per glyph. Mode 1 calls `0x10001664`, which reads into a scratch buffer and writes only non-zero pixels. The splash feature owns the renderer's entry (`p.own_entry`, 6 bytes, `sub sp,#8; push.w`) and branches it to a cave that sets mode = 1 (`[sp, #0x10]`) when r1 is the boot view's text buffer `0x2811ee38`, so only that line changes, then to the moved prologue (checked in unicorn on the patched Entry 0, `tests/test_splash.py`). Topographic image (`tools/splash_topo.py`, seed 23, 34 levels; text `CustomOS 3.80.0`; MD5 `8711c5c9d5781f3505c85a3b7b0f8d99`, **verified on unit**: the text is drawn on the picture without glyph boxes). Text `HXS OS v0.1`: MD5 `075b965b0f0ca384afaeed817964928e`, **verified on unit**. The same picture and text built through the features engine (`tools/features/splash.py`, after #10): MD5 `941b9aeae5d6ca9cbce1263a96a067f6`, Entries 1..14 and the image name, text and version pointer identical to the build before the port, **not yet tested on the unit**.

### Fonts and emoji [verified offline]

- **Loading**: `0x28db74d0` opens Entry 7 (eMMC sector `0x19408`) and Entry 8 (`0x19c09`) as streams, looks up six font names (literals `0x28db75bc..d4`: `hx21_boldFont`, `hx21_regularFont`, `hx28_boldFont`, `hx28_lightFont`, `hx35_boldFont`, `hx41_lightFont`; that order is the font number), and for each copies its Entry 7 record's glyph table into RAM at `0x28d1aa7c + font * 0x604` (BSS, not in the file): word 0 = record word 5 (extra spacing in px, 3 or 5), then 128 x 12 bytes (`0x28db7778`, at most record word 10 = 0x80 entries, from Entry 7 offset record word 11; the six tables fill Entry 7's tail `0xa740..0xcb40`). A font record has word 4 = 1 (images 0).
- **Glyph entry**: `{height, width, Entry 8 item}`, item `0xffffffff` = none. `0x28db7468(out, char, font)` gives (width, height), `0x28db744c(char, font)` the item, `0x28db748c(font)` the spacing. No bounds check: a byte >= 0x80 reads the next font's table. Glyph items are 571..958 (images 0..570); `hx21_regularFont` has 90 glyphs (space..z), all 21 px tall; every font's 0x00..0x1f slots are empty.
- **Pixels**: as images (blue on top, red at the bottom), column-major, each column bottom-up. A colour glyph drawn on a white line is copied unchanged, so its channels must be in that order: the first emoji build packed red on top and showed the guitar's red as blue **[verified on unit]**. `0x28db7844(item, ...)` reads the item's `{len, off}` from Entry 8's table (index checked against the header's count) and seeks a stream there; the blitters read one column at a time.
- **Colour**: both glyph blitters (`0x100014cc` opaque, `0x10001664` transparent) AND each pixel with the text colour, except when the colour is exactly `0xffffff` (`cmp ..., #0x00ffffff; beq`): then the glyph's pixels are copied unchanged. So a colour glyph draws in colour on a white line.
- **Boot line**: font 1 (`movs r1,#1` at `0x28d92836` before setFont), colour `0xb1b1b1` from the literal `0x28d92940` (both boot text widgets; no other reader).

### DSP cost accounting [verified offline]

The M4 decides what fits on the DSP from fixed per-model costs, not from measured load. Found by disassembly; the per-block display built on it (`src/m4/dsp_meter.s`, `tools/features/dsp_meter.py`) is verified on the unit.

- **Units**: a cost is in hundredths of a per cent of the DSP. Evidence: NAM A2 Lite declares 2345 and measures about 24% on the unit [verified on unit]; three of them (7035) plus the fixed 1500 is 8535, and the unit measured about 93% (README). Stock costs run 35..4000, median 750 (about 8%).
- **Where costs live**: the Static Model Table in Entry 0 (stock at `0x28017994`, 823 rows of 12 bytes `{u32 name_idx, u16 preset_id, u16 0, u32 cost}`, sorted by `name_idx`; `patch_amp.py add-model` relocates it and patches its pointers, so read the base from the literal at `0x28e01c08`).
- **A block's cost**: `0x28e01d50(desc, &cost)` returns 0 or a negative error. It takes a block-load descriptor: the kind byte `desc[0]` (0..0x21; kind 0 costs 0), binary-searches the table for `desc[4]` (a name index) and takes its cost; for the kinds in mask `0x30005` above 0x10 it adds the cost of `desc[8]`, the block's second model (amp+cab style blocks). Errors: `-3` for an unknown type, `-0x15` for a name index not in the table.
- **Block records** (the DSP model, `[0x28449e78]`, from `0x28e05d34(0)`): 0x54-byte records at `dsp + 0x14 + 0x54*index`. Word 0 is the block's **handle** among the preset's nodes; the 0x50 bytes after it are what `0x28e064f8` copies out for types 6/7: `rec[0]` a type byte that is 0 for effects [verified on unit, by the meter showing 0], `rec[4]`/`rec[8]` name indices (`0x28e0e2b8` compares `rec[4]` with a new block's), `rec[0xc]`/`rec[0x10]` preset IDs (`0x28e0fafc` turns them into the UI's descriptor). **This record is not a valid input to `0x28e01d50`**: its `[0]` is not the kind byte. The stock lookups take the lock `0x28e07844(0)` (mutex at `dsp + 8`) and release it with `0x28e0785c(0)`.
- **From a record to its block object**: the node table is `[dsp + 0x43fc + 4]`; `0x28dfa794(dsp + 0x43fc, handle, &p)` gives `p = [table + 0x24 + 4*handle]` (handle at most 0x4b, -1 for none), and `p[5]` is the node kind (`0x28dfa864` wants 1, a block). A block node is the preset's block object: `+0x24` flags (bit 0 in use), `+0x28` the kind byte, `+0x44` the cost, `+0x54`/`+0x70` the name indices, `+0x9f0` a handle back. `0x28e0904c(dsp, &addr, out)` + `0x28dfcac4` build a cost-function descriptor from it (`out + 4`: kind `p[0x28]`, names `p[0x54]`, `p[0x70]`), which is how `0x28e11e12` prices a block.
- **Kinds**: the block-load descriptor's kind byte (`0x28dfc2c4`, kept at block `+0x28`) is 0 for none, 1..0x15 for effects (`0x28df51ba`), 0x16 and up for others; kinds 0x10, 0x12, 0x20, 0x21 have a second model (mask `0x30005`), whose cost is added.
- **Block IDs and slots**: IDs 0..0x13 address one path (the HX Stomp has one). `0x28e07328(id, &addr)` turns IDs 1..8 and 11..18 into `{type 6, index id - 1 - 2*(id/10)}`, i.e. indices 0..7 (first row, slots 0..7) and 8..15 (second row, slots 0..7); 0, 9, 10 and 19 are other types (input, output, split/merge, presumably). Parameter IDs carry the block ID too (`0x28dd2fac`, groups of 20).
- **The UI's slot model** `0x2812c590` (from `0x28d960ac`): category bytes at `+0x37 + 16*path + slot` (slots 8..15 the second row) and on/off at `+0x27 + ...`; `0x28dd2a74(model, path, k)` tests `+0x3f + 16*path + k`, the second row. In a column with a second-row block, the Edit view shows that block (`0x28dc1a86`), so the meter takes index `k + 8` there and `k` otherwise.
- **The preset total**: `0x28dfa31c(preset)` sets `preset[0xa88]` to 1500 plus the cost at `+0x44` of each in-use block object. Block objects are at `preset + 0xaf0 + 0x9f4*k` (nine of them), in use when bit 0 of `+0x24` is set; their cost is written at block load (`0x28dfc78c`, through `0x28e01d50`). `0x28e005a8` reads `preset[0xa88]` for preset `n` at `[[r0]] + 0x6484*n`. What the fixed 1500 pays for (I/O, routing) is a [hypothesis]; an empty preset measures about 20% (README).
- **The limit**: `0x28e01e88(_, total)` is 1 when the total is at most 9000 (90%). `0x28dfae0c` computes `preset[0xa88] + cost(new) - replaced[0x44]` and passes it to that check: this is what greys out blocks in the browser. The second user of the check is at `0x28e11e84`.
- **The meter's path** (`src/m4/dsp_meter.s`): slot k -> index (k, or k + 8 for a second-row block) -> handle `[dsp + 0x14 + 0x54*index]` -> block object -> `+0x44`, under the DSP model lock.
- **Open**: what `preset[0xac4]` means in `0x28dfa31c` (it limits how many of block objects 0..4 are summed; objects 5..8 always count); whether a block's real load tracks its declared cost (NAM: 23.45% declared, about 24% measured).

### Text widgets and fonts [verified offline]

- **Fonts**: six, in the image store (Entry 7 records 571..576). At boot `0x28db74d0` looks each up by name and stores its index at `0x280021ac + 4k`, so the **font number** k a text widget takes is: 0 `hx21_boldFont`, 1 `hx21_regularFont`, 2 `hx28_boldFont`, 3 `hx28_lightFont`, 4 `hx35_boldFont`, 5 `hx41_lightFont`. A font's record has 128 glyph records `{height, width, Entry 8 item}` (item -1 = none) at Entry 7 offset word 11 (`0xa740 + 0x600 * n`), copied at boot to `0x28d1aa7c + 0x604 * font` (accessors `0x28db741c`, `0x28db744c`, `0x28db7468`). Fonts 1, 2, 3 and 5 cover ASCII 32..122; **0 and 4 have only `0-9A-D`** (preset numbers).
- **Text widget** (ROM, 0x30 bytes): `[0]` text pointer, `[4]` own-buffer size, `[8]`/`[0xc]` x, y, `[0x10]`/`[0x14]` measured w, h, `[0x18]` font, `[0x1c]` colour `0xRRGGBB`, `[0x20]` anchor, `[0x24]` own buffer, `[0x2a]` visible, `[0x2c]` node (0x28 bytes, as for rectangle widgets). Every setter stores, re-measures if needed and marks the node dirty; nothing repaints until `0x28db8508(0, 1)`.
- Calls (app PLT stub → ROM): init `0x28e249d0(w, node)` (`0x100023e8`; visible = 1); own buffer `0x28e24bf0(w, buf, size)` (`0x1000237c`); setText `0x28e24bc0(w, str, len)` (`0x10002124`; copies into the own buffer when there is one, then measures with the app's `0x28db78d8`); setPos `0x28e24a68(w, x, y)` (`0x100021e8`); setFont `0x28e249e8(w, k)` (`0x10002294`); setColor `0x28e24a28(w, rgb)` (`0x10002264`); setAnchor `0x28e24ac8(w, a)` (`0x10002324`); setVisible `0x28e24bc8(w, v)` (`0x10002394`). Paint: erase `0x28e24c90(fb, fb, w)` (`0x10002038`), draw `0x28e24c30(fb, fb, w)` (`0x1000206c`, which calls the app's draw-text `0x28db7aa4(fb, str, len, x, y, font, colour, anchor, 0)` through the ROM veneer `0x10003530`).
- **Anchor** (`0x1000139c`): a = 3 * row + column. Column 0/1/2 offsets x by 0, w/2, w; row 0/1/2 offsets y by 0, h/2, h. The blit (`0x100014cc`) draws rows from y - offset upwards (y counts up from the bottom, pixel x * 240 + y), so column 0 puts x at the left edge and row 2 puts y at the top edge: anchor 6 is the top left corner. The rectangle widgets' "layer" 6 is this anchor, which is why their y is the top edge.

### Tempo (BPM) [verified offline]

- The tempo is a Global Setting: **ID 14** Tempo Select (0 Snapsht, 1 Preset, 2 Global), **ID 15** Global BPM, **ID 16** Preset BPM. The stock code always picks the BPM setting as `ID 14 == 2 ? 15 : 16` (tap `0x28d9bfa8`, tempo screen `0x28d91368`).
- `GET_VALUE(15 or 16, out)`: `[out]` type byte 3 (float), `[out+4]` the BPM as a float. The tap tempo stores 60e6 / (mean of the last 8 intervals in µs), clamped to 40..240, with the settings setter `0x28e1f8f4(ctx, id, &value, 3)`.
- The tap tempo screen (constructor `0x28dcc8d4`, title `Tempo`, rows `0x28d91248`/`0x28d911a8`) shows the BPM from `0x28e04aa0(0x28d92a98(), out)`: a 5-byte record `{byte, float}` from the current preset's object (`+0xb09` when its byte `+0xb08` is set, else `+0xb0e`), and `Extrnl` instead while the flag `0x28d9685c()` (byte `0x2812bd90`) is set. **[hypothesis]** That flag is external MIDI clock, and the record is the snapshot or preset tempo.
- **[hypothesis]** `GET_VALUE(16)` follows the current snapshot's tempo when Tempo Select is Snapsht.
- **Front panel LEDs** [verified offline]: three (0..2), the footswitch rings; footswitch k has LED k. `0x28d98f74(led, rgb)` sends a colour to the panel's LED controller (over 100 callers, every LED change); it starts `push {lr}; ldr r3,=0x281c90a4`. The driver keeps per LED a colour `0x281f35e0 + 3i`, a mode `0x281f35f8 + i` (0 off, 1 on, 2 blink; `0x28db8260(led, mode)`) and a half period `0x281f3608 + 4i` (`0x28db8138(led, period)`). The LED task `0x28db7f04` (started from `0x28db843c`) loops with `0x28e24c58(1000)` (the ROM sleep `0x10000830` waits (us + 9) / 10 ticks of 10 µs, so a turn takes 1 ms plus its work) and toggles mode-2 LEDs at `0x28db7f9a`. **[verified on unit]** The TAP footswitch's blink does not come through that toggle (a hook there never saw it) but does go through the LED send, and it keeps time with a metronome.
- **Footswitch functions** [verified offline]: `0x28d9607c()` returns `0x28128a70`; footswitch k's function is the byte at `0x28128a74 + 2k`, and 1 is TAP (the footswitch switch at `0x28dd14e0` reaches the tap call `0x28dd1656` for value 1).
- **The stock beat** [verified offline]: a task loop from `0x28d9bdfc` sleeps 1 ms (`0x28e24c58(1000)`), then reads the µs clock `0x28da6458()` into `0x281cd070`. While its enable byte `0x281ccc48` is set and footswitch 3 (`[0x28128a78]`) is TAP, it turns the beat once more than half the period `0x281ccc44` (whole ms, set by `0x28d9bef8`) has passed since the last turn `0x281cd074` (µs; `(now - last) / 1000 > period / 2`). At each turn it moves the last turn on by `period * 1000 / 2`, flips the phase byte `0x281ccc49`, and sets LED 2 on (`0x28db81fc` colour, then `0x28db8260(2, 1)`) or off (`0x28db8260(2, 0)`). In every other case it sets the last turn to now, so **without a TAP footswitch the stock keeps no beat**. The period is `u32(60000.0f / tempo)` (`0x28dd0af6`, literal `0x476a6000`). `0x28dd0ab8` skips all of this while the byte `0x28128260` is 5.
- **No TAP footswitch** [verified on unit]: in Preset and Snapshot footswitch modes no footswitch is TAP, so no ring blinks (as on stock).
- **Tap Tempo LED** (setting 26) is read at only two places that decide to blink: `bl GET_VALUE` at `0x28d9c116` (the tap core) and `0x28dd0ae2` (in `0x28dd0ab8(obj, k)`, k the TAP footswitch).
- **Microsecond clock** [verified offline]: `0x28da6458()` (`0x28da37ac(1)`, a hardware timer register) is what the tap tempo times taps by (BPM = 60e6 / interval).

## The M4 to DSP link [verified on unit]

- Framed 1 KB (256-word) SPI/DMA frames. Word 0 is magic `0xFACEF00D`, word 255 is trailer `0xD00FECAF`, payload from word 2.
- The M4 receive callback is reached through a literal at `0x28da6134` (stock value `0x10001095`; `r1` = RX buffer). Hooking it by replacing the literal and tail-calling the stock address works.
- The M4 sees halfword-swapped words: `ror #16` to read them.
- Most frames are empty. Words ~70..254 are unused filler.
- **The DSP can send data to the M4 by writing into the frame tail.** A SHARC routine scanned DSP memory (internal `0x80000..0x100000`, DDR2 `0x200000..0x330000`, 256 words per call) for `0xFACEF00D` with `0xD00FECAF` at +255, wrote `0x600DF00D` at word 200, a tag at 201 and a call counter at 202, and all three arrived at the M4. Word 203 onward is free. This is the transport for DSP-measured values (for example gain reduction), and it needs no knowledge of Line 6's own message formats.
- Searching Line 6's existing message traffic for a meter value ("needle in a haystack") was tried and abandoned.

## The SHARC (DSP) side

- `tools/sharc/sasm.py`: assembler. `tools/sharc/ssim.py`: simulator (the `MANT` ALU op `0xAD` is not modelled). There is no disassembler in the repo. Labels are case-insensitive (`fp_cur` clashes with `FP_CUR`). `IF EQ DM(I5,1) = I4` is illegal: copy to a data register first.
- `tools/sharc/nam_multi.py` generates the NAM A2 Lite kernel (checked in the simulator against `src/sharc/nam_a2.asm`).
- **Primitive registry**: in Entry 2's data at DM `0x200000`, 2256 words, 8-word entries `[id, init_fn, 0, 0, ctrl_fn, process_addr, dm_words, pm_words]`. A primitive's process code address is word 5.
- **Registry-wrap technique [verified on unit for the transport]**: `tools/patch_amp.py patch --wrap-prim ID:ADDR` repoints a registry entry's process address at a custom kernel, which `CALL`s the stock address first (`ORIG`) and then does its own work. The patch asserts that the stock address equals `ADDR`, and adds a new tag-4 LDR block. No graph surgery is needed.
- Custom kernels: save and restore what they use (MODE1, R0..R7, I4..I6, L4..L6); clear `PEYEN|BDCST9` while running.
- A kernel is installed as the entry of an otherwise unused primitive; `patch_amp.py patch --asm file.asm` places code at the addresses the `.section` lines give.

### Deluxe Comp [verified offline]

- Model `HD2_CompressorDeluxeCompMono`, composite `0x6000c9`, members: 0 in-port, 1 `0x239d`, 2 and 3 `0x102`, 4 `0x271a` (compressor core, 2 inputs / 1 output), 5 `0x89` (2 inputs), 6 `0x80`, 7 out-port.
- Registry entry for the core at `0x200320`: `[0x271a, 0x6100f8, 0, 0, 0x6100bd, 0x8d9c9, 0xb, 5]`; process code at PM `0x8d9c9`, which uses `MANT` (log-domain gain).
- The wrapper was called with `I1=0x967de`, `I2=0x967ee` (adjacent 16-word buffers), `I3=0xb2e30`, `I0=0x96fc9`, `I4=0xe14ee`, `I5=0xc5b52`. Sample magnitudes were tiny (~1e-5) in a probably silent capture, so **which buffer is the compressor's input and which its output is unknown.**
- Blocks are 16 samples.

### Control functions [verified offline]

- **[verified on unit]** A primitive's control function is called as (pid R4, pointer to the value R8, the core's state R12). R8 is one slot shared by all pids, followed by the writers {pid, 1, core}; R12's first words are the core's DM block (start, end, start), then its PM block. The value is not on the stack (`DM(1, I6)`) or in the core's state.

- A registry entry's `init_fn`/`ctrl_fn` addresses such as `0x6100bd` are VISA (16/32/48-bit) code in DDR2: short-word address `0x600000 + 2 * (word - 0x300000)`, from Entry 2's tag-10 boot blocks at `0x300000`. In each 32-bit word the low half is the first parcel: in that order, the 48-bit `MODIFY(I7,-2)` (`1607fffffffe`) occurs 229 times. `ssim.py` does not run VISA, and its 16/32-bit encodings are not in the repo.
- The parcels `70be`/`70fe` (the first parcels of `R0 = R8` / `R0 = R12`) open the generic store `0x611ddd`, and `4dfe 0e..` (`I12 = DM(M7, I6)`) appears early in `0x6100bd`: consistent with the C calling convention (arguments in R4, R8, R12).
- In the Deluxe Comp, no member primitive uses the generic store: `0x239d` has none, and `0x102`, `0x271a`, `0x89`, `0x80` each have their own.

### Model parameters (Entry 3, Entry 4 parameter map, Entry 0 info row) [verified offline]

- A model's parameter count has to agree in three places: Entry 3's descriptor (`d[7]` parameters, `d[6]` states), the blob's parameter map (one input node and one slot-map entry per parameter), and the Entry 0 UI Model Info Table row (bytes 24..35, three counts).
- Parameter map header: offsets of tables A (nodes), B, C (edges), D (slot map), E and F at words 0, 2, .. 10; sizes at 12..17; counts nA..nF at 18..23. The sizes follow the tables in every map checked: sum of node state words, nA, nD + sum n_out + inputs, nC + nD + inputs, nD, nE.
- Deluxe Comp (blob 68 mono, 349 stereo): seven input nodes, op `0xa` float or `0xb` int (Ratio). Slot map {node, state index, slot, 0}; state index = the input's rank in node order, matching Entry 3's state records `{0, 0x80b98, name, type, index}`. Root init records `{path [1, 0], slot, value, kind 1}` give each slot's default.
- `tools/patch_comp.py` adds GR Position, GR Direction and GR Thickness (int lists, slots 8..10) to both Deluxe Comps. The new input nodes have no edges, so the DSP is unchanged. Entry 3's tail string section grows in place, and the model table and everything after it move down. The blob's map, init records and relocation list are rebuilt after the node tree.

## Open problem: the gain-reduction meter

Goal: on the Home divider, a green bar grows left to right with the gain reduction of the first or active compressor (start with the Deluxe Comp), the rest black, maximum reduction = full width. The reduction must be computed on the device.

Design as built:

1. **DSP**: the wrapper around primitive `0x271a` measures the peak of three candidate buffers before and after the stock call, and writes these into every validated frame tail: words 207..209 = pre-call peaks of buffers A (`I1`), B (`I2`), C (`I3`); 210..212 = post-call peaks; 203..206 the register values; 213..215 samples.
   Words 216, 217: the max of A before and B after over 128 blocks.
2. **M4** (`src/m4/gr_meter.s`): receive hook. Reads the settings **GR Input** and **GR Output** (each picks buffer A, B or C), computes GR = 1 - post/pre in Q16 with integer maths, smooths (up instantly, down slowly), maps to 0..320 px in 8 px steps over the four segments, and calls `setColor`/`setSize` only when a segment changes.
